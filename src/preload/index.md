# Preload 脚本说明文档

## 概述

Electron 预加载脚本（Preload Script），是连接主进程（Node.js 后端）和渲染进程（前端页面）的安全桥梁。该文件在渲染进程加载之前执行，负责通过 Electron 的 contextBridge API 将主进程的功能安全地暴露给前端页面。

该文件解决了 Electron 应用中的安全隔离问题，确保前端页面可以直接调用后端功能，同时保持系统的安全性。

## 核心功能

### 主要能力

- **API 桥接功能**：将主进程的 IPC（进程间通信）接口封装为前端可调用的异步 API
- **安全隔离**：使用 contextBridge 在隔离的上下文中暴露 API，防止恶意代码访问 Node.js 功能
- **模块化组织**：按功能领域分组定义 37 个 API 方法，提供清晰的代码结构
- **错误处理**：包含全局错误捕获和详细的日志输出，便于调试
- **类型简化**：使用 any 类型简化参数传递，由前端和后端各自维护详细的类型定义

### 关键操作

1. **API 对象创建**：为 8 个功能模块分别创建 API 对象
2. **API 合并**：使用展开运算符将所有模块的 API 合并为统一的 electronAPI 对象
3. **API 暴露**：通过 contextBridge.exposeInMainWorld 将 API 安全暴露到 window.electronAPI
4. **日志记录**：在关键步骤输出详细日志，包括模块创建、合并、暴露等过程

### 功能分组

该脚本将 37 个 API 方法分为 8 个功能模块：

- **聊天相关**（5个方法）：发送消息、获取历史、重置对话、检查 API Key、获取会话列表
- **团队管理**（4个方法）：列出团队、创建团队、删除团队、获取所有团队及其 Agent
- **Agent 管理**（5个方法）：列出 Agent、创建 Agent、更新 Agent、删除 Agent、获取单个 Agent
- **会话管理**（6个方法）：列出会话、创建会话、获取会话、更新会话、删除会话、获取或创建会话
- **消息历史**（4个方法）：列出消息、添加消息、删除消息、清空消息
- **AI 配置管理**（5个方法）：获取配置、保存配置、验证 API Key、重置为默认值、检查 API Keys 是否已配置
- **CWD 管理**（4个方法）：选择工作目录、验证工作目录、获取会话 CWD、获取默认工作目录
- **主理人 Agent**（4个方法）：获取主理人 Agent、与主理人对话、获取对话历史、重置对话

## 依赖关系

### 谁使用此文件

| 使用者 | 用途 | 位置 |
|--------|------|------|
| windowManager.ts | 在创建 BrowserWindow 时指定此文件为预加载脚本 | src/main/windowManager.ts |
| 渲染进程页面 | 通过 window.electronAPI 调用后端功能 | 所有前端组件和 Hooks |

### 此文件使用的依赖

| 依赖项 | 用途 | 来源 |
|--------|------|------|
| electron (contextBridge) | 安全地将 API 暴露到渲染进程 | Electron 内置模块 |
| electron (ipcRenderer) | 与主进程进行 IPC 通信 | Electron 内置模块 |

### 集成点

1. **主进程集成**：通过 windowManager.ts 中的 preload 配置加载
2. **前端集成**：前端通过全局 window.electronAPI 对象调用后端功能
3. **IPC 通信**：所有 API 调用最终通过 ipcRenderer.invoke 转发到主进程的对应 handler

## 代码风险和异味

### 安全问题

| 风险项 | 严重程度 | 位置 | 说明 |
|--------|----------|------|------|
| **类型安全缺失** | 中等 | 所有方法 | 使用 any 类型绕过类型检查，可能导致运行时错误 |
| **参数验证缺失** | 中等 | 所有方法 | 前端可能传递错误类型或格式的参数，主进程需要二次验证 |
| **错误处理不完整** | 低 | try-catch 块 | 虽然有全局错误捕获，但单个 API 方法没有独立的错误处理 |

### 代码异味

| 异味项 | 严重程度 | 位置 | 说明 |
|--------|----------|------|------|
| **过度使用 any 类型** | 中等 | 第72、79、108行等 | 使用 any 类型降低类型安全性，应使用具体的接口定义 |
| **日志污染** | 低 | 第3、209、228行等 | 生产环境保留大量调试日志，应考虑条件编译 |
| **缺少返回类型** | 低 | 所有 async 方法 | 方法缺少明确的返回类型注解，降低代码可读性 |
| **错误堆栈可能丢失** | 低 | 第242行 | 对于非 Error 类型的错误，堆栈信息显示为 'No stack' |

### 错误处理

- **全局错误捕获**：使用 try-catch 包裹所有 API 创建和暴露逻辑
- **错误日志记录**：捕获错误时输出详细的错误信息和堆栈
- **错误传播**：API 调用失败时，错误会通过 Promise rejection 传播到前端

### 资源管理

- **无资源泄漏风险**：该文件不直接管理任何资源（如文件句柄、网络连接等）
- **IPC 通信**：所有 IPC 调用都是异步的，由 Electron 框架管理连接

### 并发问题

- **无并发风险**：该文件本身不涉及并发操作，所有方法都是异步函数

## 如何测试

### 单元测试策略

由于该文件运行在 Electron 的特殊环境中，单元测试比较困难。建议采用以下策略：

1. **集成测试为主**：通过启动完整的 Electron 应用进行测试
2. **API 模拟测试**：在测试环境中模拟 window.electronAPI 对象
3. **IPC 通信测试**：编写测试主进程的 handlers，确保 IPC 通信正常

### 集成测试考虑

**测试环境准备**：
- 启动完整的 Electron 应用
- 打开开发者工具查看 preload 脚本加载日志
- 验证 window.electronAPI 对象是否正确暴露

**关键测试场景**：
1. **API 暴露验证**：在开发者工具 Console 中执行 `Object.keys(window.electronAPI).length === 37`
2. **各模块 API 验证**：逐一测试每个模块的 API 是否可调用
3. **IPC 通信验证**：调用 API 后，主进程是否正确收到请求
4. **错误处理验证**：传递错误参数时，是否能正确返回错误信息

### 边界案例覆盖

| 测试场景 | 预期行为 | 验证方法 |
|----------|----------|----------|
| 前端调用不存在的 API | 返回 undefined 或抛出异常 | 在 Console 中调用 window.electronAPI.nonExistentMethod() |
| 传递空参数或错误类型 | 主进程返回错误信息 | 调用 window.electronAPI.chat(null, null, null, null) |
| 主进程 handler 抛出异常 | 错误通过 Promise rejection 传播到前端 | 模拟主进程 handler 抛出异常 |
| 快速连续调用同一 API | 每个 API 调用都独立处理 | 在循环中多次调用同一 API |

## 注意事项

### 性能考虑

- **IPC 通信开销**：每次 API 调用都需要跨进程通信，应避免频繁调用
- **序列化开销**：大对象在 IPC 传递时需要序列化，注意传递的数据大小
- **日志性能影响**：生产环境应考虑移除或禁用调试日志

### 配置要求

- **Electron 版本**：需要 Electron 30.0.0 或更高版本
- **TypeScript 编译**：需要编译为 CommonJS 格式（.js 文件）
- **预加载路径**：必须在创建 BrowserWindow 时正确指定 preload 脚本路径

### 环境依赖

- **Node.js 集成**：必须设置为 false（nodeIntegration: false）
- **上下文隔离**：必须设置为 true（contextIsolation: true）
- **沙盒模式**：在沙盒环境中运行，无法直接访问 Node.js API

### 常见陷阱

1. **模块导入问题**：不能使用 import 语句导入本地模块，必须在单个文件中 inline 定义所有 API
2. **this 绑定问题**：确保所有方法使用箭头函数或正确绑定 this
3. **异步处理**：所有 API 调用都是异步的，前端必须使用 async/await 或 .then() 处理
4. **类型定义分离**：前端的 TypeScript 类型定义在单独的 .d.ts 文件中，不在此文件中定义

### 维护建议

- **添加新 API 时**：遵循现有的模块化结构，添加到对应的功能模块中
- **修改现有 API 时**：确保前后端的类型定义同步更新
- **日志管理**：在发布版本前考虑移除或条件编译调试日志
- **错误处理增强**：为关键 API 添加更详细的错误类型和错误信息
