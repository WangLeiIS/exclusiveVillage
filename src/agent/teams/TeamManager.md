# TeamManager 说明文档

## 概述

TeamManager.ts 是团队管理器类，专门负责团队的生命周期管理。该类提供团队的创建、列出和删除功能，是系统中团队资源的核心管理器。

该文件专注于团队级别的操作，而团队内部的 Agent 管理由 TeamAgentManager 负责。每个团队都有独立的数据库存储，通过 DatabaseManager 进行数据持久化。

## 核心功能

- **团队列表查询**：扫描并返回所有有效的团队信息，包括团队名称和 Agent 数量统计
- **团队创建**：创建新团队并自动初始化默认的 vocal agent（团队助手）
  - 默认助手名称格式：`{团队名}-assistant`
  - 自动生成描述信息和角色设定
- **团队删除**：删除团队及其所有相关数据（包括整个数据库文件目录）

## 依赖关系

### 该文件使用的依赖

| 依赖项 | 用途 |
|--------|------|
| DatabaseManager | 数据库操作的基础类，负责团队数据库的连接和管理 |
| Logger | 日志系统，记录操作日志和错误信息 |
| fs (Node.js) | 文件系统操作，用于扫描团队目录和删除团队数据 |
| path (Node.js) | 路径处理，用于构建文件系统路径 |

### 使用该文件的模块

| 使用者 | 用途 |
|--------|------|
| src/main/handlers/teamHandlers.ts | 主进程中处理团队相关的 IPC 通信 |
| src/main/handlers/sessionHandlers.ts | 查询团队列表用于会话管理 |
| src/main/handlers/messageHandlers.ts | 查询团队列表用于消息路由 |
| src/main/migrations/migrateTo_v0.2.0.ts | 数据迁移时查询团队列表 |
| src/agent/teams/TeamAgentManager.ts | 综合查询时需要获取团队列表 |

### 集成方式

TeamManager 通过单例模式导出 `teamManager` 实例，所有处理器直接导入该单例使用团队管理功能。每个团队对应一个独立的数据库文件，存储在 `agents-dir/{团队名}/agents.db` 路径下。

TeamManager 与 DatabaseManager 和 TeamAgentManager 协同工作：
- DatabaseManager 负责底层数据库操作
- TeamAgentManager 负责团队内的 Agent 管理

## 代码风险和异味

### 安全问题

- **SQL 注入风险**：多处使用字符串拼接构建 SQL 查询，存在严重的安全隐患
  - 第 171 行：`SELECT * FROM agents WHERE name = '${config.name}'`
  - 第 241 行：`DELETE FROM agents WHERE name = '${agentName}'`
  - 第 256 行：`SELECT * FROM agents WHERE name = '${agentName}'`
  - 攻击者可以通过构造特殊的 agentName 来执行任意 SQL 命令

- **缺少输入验证**：所有公共方法都没有验证输入参数的合法性和安全性
  - `createTeam` 和 `createAgent` 没有验证名称格式，可能导致路径遍历攻击
  - 没有检查团队名称或 Agent 名称是否包含特殊字符（如 `../`）
  - 没有验证描述、角色等字段的长度和内容

### 错误处理

- **静默失败**：创建团队时的 vocal agent 创建失败不会阻止团队创建，可能导致不一致状态
- **团队不存在**：删除不存在的团队会抛出错误，但调用方可能没有适当处理

### 资源管理

- **数据库连接管理不当**：每个方法都手动调用 `connect` 和 `close`，存在资源泄漏风险
  - 如果中间操作抛出异常，`close` 不会被调用
  - 没有 try-finally 保证连接一定会被关闭

- **动态导入开销**：`fs` 和 `path` 模块在每次方法调用时都会动态导入，而不是在文件顶部一次性导入

### 代码质量问题

- **职责委托**：创建团队时需要委托给 TeamAgentManager 创建默认 Agent，增加了模块间耦合
- **文件系统操作**：`deleteTeam` 直接操作文件系统删除目录，操作不可逆

### 并发和竞态条件

- **团队删除竞态**：如果在 `listTeams` 和具体操作之间团队被删除，可能导致不一致
- **无并发控制**：如果多个请求同时创建或删除同一团队，可能导致数据竞争

## 如何测试

### 单元测试策略

- **团队管理测试**
  - 创建团队：验证团队能够正确创建，并且自动创建了默认的 vocal agent
  - 列出团队：验证能够正确扫描并列出所有有效的团队
  - 删除团队：验证团队目录和数据库文件被正确删除
  - 删除不存在的团队：验证抛出适当的错误

- **Agent 管理**
  - 创建 Agent：验证 Agent 能够正确创建并保存到数据库
  - 列出 Agent：验证能够返回团队中的所有 Agent
  - 更新 Agent：验证允许的字段能够正确更新
  - 删除 Agent：验证 Agent 被正确删除
  - 获取 Agent：验证能够返回正确的 Agent 信息

- **边界情况**
  - 创建同名团队：验证系统如何处理重复创建
  - 创建同名 Agent：验证数据库约束是否生效
  - 空团队：验证没有 Agent 的团队能够正常列出
  - 特殊字符名称：测试包含空格、特殊字符的团队和 Agent 名称

### Mock 和 Stub 建议

- **Mock DatabaseManager**：创建 mock 对象来模拟数据库操作
  - 模拟 `connect` 返回预定义的数据库实例
  - 验证 SQL 查询是否正确执行
  - 验证参数绑定是否正确

- **Mock Logger**：验证日志记录是否正确调用
- **Mock fs 模块**：模拟文件系统操作，避免在测试中创建真实文件
- **使用内存数据库**：配合 DatabaseManager 使用内存数据库进行快速测试

### 集成测试考虑

- **真实数据库操作**：使用真实的 SQLite 数据库测试完整的 CRUD 流程
- **文件系统操作**：验证在文件系统上正确创建和删除团队目录
- **自动创建 vocal agent**：验证创建团队时默认 Agent 能够正确创建

### 安全测试

- **SQL 注入测试**：尝试在 agentName 和 teamName 中注入恶意 SQL 语句
- **路径遍历测试**：尝试使用包含 `../` 的名称访问系统文件
- **输入长度测试**：测试超长名称是否导致缓冲区溢出或数据库错误

### 测试组织建议

建议创建 `src/agent/__tests__/TeamManager.test.ts` 文件，使用 Jest 或类似测试框架。每个方法都应该有独立的测试用例，使用 beforeEach/afterEach 确保测试之间的隔离。

## 注意事项

### 性能考虑

- **数据库连接开销**：每个操作都会打开和关闭数据库连接，频繁操作时可能影响性能
- **文件系统扫描**：`listTeams` 需要扫描文件系统并连接每个团队的数据库，团队数量多时可能较慢

### 配置要求

- **DatabaseManager 依赖**：必须正确配置 DatabaseManager，包括 AGENTS_DIR 环境变量或默认路径
- **TeamAgentManager 依赖**：创建团队时需要 TeamAgentManager 来创建默认 Agent
- **文件系统权限**：需要有创建和删除目录及文件的权限
- **预置数据库**：创建团队时需要 metadata 目录中有对应的预置数据库文件

### 使用流程

- **必须先有 DatabaseManager**：TeamManager 依赖 DatabaseManager，必须确保 DatabaseManager 正确初始化
- **团队隔离**：每个团队的数据完全隔离，Agent 操作必须指定团队名称
- **自动创建 vocal agent**：创建团队时会自动创建默认助手，这个操作失败不会阻止团队创建

### 常见陷阱

- **团队删除不可恢复**：删除团队会删除整个目录和数据库文件，数据无法恢复
- **数据库连接泄漏**：如果方法在关闭连接前抛出异常，可能导致连接泄漏
- **并发操作风险**：多个请求同时创建或删除同一团队可能导致数据不一致
- **TeamAgentManager 依赖**：创建团队时需要 TeamAgentManager 可用

### 维护建议

- **修复 SQL 注入**：将所有字符串拼接的查询改为参数化查询（最高优先级）
- **添加输入验证**：验证所有输入参数的格式、长度和安全性
- **改进错误处理**：为每个方法添加完善的错误处理和资源清理
- **使用连接池**：考虑使用数据库连接池，而不是每次操作都开关连接
- **添加事务支持**：对于复杂的操作，使用数据库事务确保数据一致性
- **添加并发控制**：使用锁或其他机制防止并发操作导致的数据竞争
- **优化查询性能**：对于 `getAllTeamsWithAgents`，考虑使用批量查询或缓存
